## 一、结论摘要

1. **原项目没有 `member:manage`、`skill:publish` 这类统一权限 Key**，也没有 CASL、RBAC、ACL 库。`package.json` 中不存在 `casl / accesscontrol / rbac / permission / ability` 依赖。
2. 实际权限模型是 **多层叠加**，共 6 个来源：
   - 会话身份（`lx / itar / org / coach`）
   - 业务角色 `boss / finance / teaching`
   - 岗位树 `root / child / seat` + 角色包（Skill / 产线白名单）
   - 技术等级 `L1 / L2 / L3`（能力位）
   - MCP 令牌六维 scope
   - 租户 / 机构 entitlement（`all / deny / allow`）+ 共享授权包 grants
3. **不是纯角色绑定，也不是标准的「角色 + 权限点多选」**：更接近「角色包白名单 + 等级能力位 + 数据范围」；没有任何「用户 ↔ 权限点」的勾选表。
4. 授权数据主要落在 **JSON 文件 / SQLite**（`vault/members.json`、`vault/role-packs.json`、`vault/grants.json`、`mcp-tokens/tokens.sqlite`），不是数据库权限表；改造为多选勾选架构时，**必须补数据模型，不能只改前端**。
5. **前端过滤范围很大，但服务端强制点不完整**：约 2/3 的 API 没有岗位级授权，前端隐藏不能当作安全边界。

## 二、权限模型总览

### 2.1 六层结构

| 层 | 载体 | 解决什么问题 | 代码位置 |
|---|---|---|---|
| 1. 身份/会话 | `jxf_session` HMAC 票据，subject 前缀 `lx: / itar: / org: / coach:` | 是否登录、属于哪类主体 | `lib/auth.ts#L72-L193` |
| 2. 业务角色 | `users.role = boss / finance / teaching` | 财务、教学、员工档案的模块级可见性 | `lib/lx-roles.ts#L8-L63` |
| 3. 岗位树 + 角色包 | `root / child / seat`，包 = `{skills[], automation[]}` | 这个岗位能用哪些 Skill / 产线 | `lib/projects.ts#L11-L39`、`lib/role-capabilities.ts#L390-L605` |
| 4. 任用与等级 | `Assignment{principalId, roleId}` + `accessLevel L1/L2/L3` | 这个人被雇到哪些岗位、能做多危险的动作 | `lib/members.ts#L13-L30`、`lib/access-level.ts#L22-L85` |
| 5. MCP 令牌 scope | profile / skills / pipelines / ship / directWrite / knowledgeWrite / tools / denyTools | 外部 AI 客户端能调用哪些工具、改哪些 Skill | `lib/mcp/token-store.ts#L18-L67`、`lib/mcp/scope.ts#L1-L268` |
| 6. 租户/机构 entitlement + grants | `all/deny/allow`、`pack/channel` | 套餐开关、跨岗位共享目录 | `lib/policy.ts#L1-L115`、`lib/grants.ts#L1-L120` |

### 2.2 实际判定链（以后端为准）

```text
请求进入
→ middleware：AUTH_SECRET 是否配置（fail-closed 503）
→ 是否企业版禁用路径（404）
→ 是否公开路径 / 是否需登录
→ MCP 令牌 / 内部密钥 / desk runner token / 普通会话
→ 主体类型限制（coach 只能本企业清单；org 只能音乐接口）
→ 路由内：
    a) requireWorkbenchAdmin / requireHworkAdmin / actorCanManage
    b) 业务角色（boss/finance/teaching）
    c) 岗位任用（hasAssignment / assertAssignment）
    d) 等级能力位（capabilitiesOf）
    e) MCP token scope（assertTokenScope）
    f) 数据归属（org_id / project_id / session owner）
```

### 2.3 三种「角色」概念必须区分

| 名称 | 取值 | 作用域 | 易混点 |
|---|---|---|---|
| 业务角色 `LxRole` | `boss / finance / teaching` | 经营台模块 | 与岗位树无关 |
| 岗位 `Project.type` | `root / child / seat` | 工作台组织 | 与等级无关 |
| 技术等级 `AccessLevel` | `L1 / L2 / L3` | 危险动作阈值 | 与岗位无关，`title` 是自由文本 |

> 原项目注释明确写了「业务角色与等级互不推导」（`lib/access-level.ts#L1-L6`），但 `admin ⇔ L1` 又有互相写入逻辑，这是双轨点之一。

### 4.2 绑定模式判定

| 问题 | 结论 | 证据 |
|---|---|---|
| 是纯角色绑定吗？ | **不是**。角色只决定「模块/分类可见」，具体 Skill/产线由角色包决定 | `skillsForRole`、`automationForRole` |
| 是标准 RBAC 吗？ | **不是**。没有 `roles / permissions / role_permissions` 表，也没有权限点字符串 | 全仓无权限表或 CASL |
| 是「角色 + 权限点多选」吗？ | **不是**。只有等级能力位 + 布尔/数组 scope，没有用户级勾选 | `capabilitiesOf`、`McpTokenScope` |
| 数据范围在哪？ | 岗位树 + 目录（`vault/projects/<root>/...`）+ grants | `projects.ts`、`grants.ts` |
| 授权存储在哪？ | JSON / SQLite，而不是数据库 ACL | `vault/members.json`、`vault/role-packs.json`、`tokens.sqlite` |

### 4.3 权限判定的实际优先级（按代码调用顺序整理）

```text
1. 环境与版本
   - AUTH_SECRET 不合格 → 503
   - 企业版禁用模块 → 404
2. 主体身份
   - 未登录 → 401 / 跳登录
   - coach/org 主体 → 仅允许受限路径
3. 平台管理权
   - requireWorkbenchAdmin / requireHworkAdmin / actorCanManage
4. 业务角色
   - boss / finance / teaching（分类与动作）
5. 岗位任用
   - hiredRoleIds / hasAssignment / assertAssignment
6. 等级能力
   - capabilitiesOf(level)（manageMembers / issueTokens / codeScope / protectedPaths / ssh）
7. 范围与套餐
   - 角色包 → 租户 entitlement → 机构 capability
8. 令牌 scope
   - profile / skills / pipelines / ship / directWrite / knowledgeWrite / tools / denyTools
9. 数据归属
   - org_id / project_id / session owner / 目录路径
```

> 注意：不同入口并不完全按同一顺序执行，存在「有的接口只做 2+9，有的做 1~8」的不一致，见第六节风险清单。

## 七、面向多选勾选架构的迁移映射建议

> 以下为分析建议，本次未做任何代码修改。

### 7.1 三轴拆分（关键）

多选勾选架构不应把三件事塞进一个权限点：

| 轴 | 内容 | 建议承载 |
|---|---|---|
| **功能权限点** | 能做什么动作（查看/新增/修改/删除/审批/导出） | `permissions` + 用户/角色勾选 |
| **数据范围** | 能对哪些部门/岗位/自己/子树的数据做 | `scope`（department_id / role_id / self） |
| **阈值与审批** | 高危动作是否需要二级确认/审批 | `approval_policy`（如 ship、付款、投放确认） |

### 7.2 建议保留的权限点

- 人员：`member:view / create / update / remove / level:update / ssh:manage / quota:manage`
- 组织：`org:node:view / manage`、`org:grant:read / write / manage`
- Skill：`skill:view / use / create / author / code:write / ship`
- 产线：`pipeline:view / run / manage / mode:switch`
- 知识：`knowledge:read / write / confirm / delete / scout / source:manage / handover:export`
- 令牌：`token:issue / revoke / scope:edit`
- 审计与平台：`audit:read`、`platform:settings:manage`、`platform:tenant:manage`、`platform:upgrade`
- 经营台：`finance:reimbursement:*`、`finance:ledger:write`、`finance:open-item:write`、`finance:capital:write`、`teaching:student:*`、`teaching:payment:*`、`teaching:session:*`、`staff:manage`
- 投放：`ads:manage / approve`

### 7.3 需要拆分或改造的权限点

| 原设计 | 问题 | 建议 |
|---|---|---|
| `manageMembers: boolean` | 粒度过粗 | 拆成 `member:create/update/remove/level/ssh/quota` |
| `codeScope: "*" \| "packs"` | 无法表达具体 Skill | 改为 `skill:code:write` + `skill_ids[]` 数据范围 |
| `protectedPaths: boolean` | 这是系统不变量，不应可勾选 | 保留为服务端硬编码，**不进入权限勾选** |
| `admin: boolean` + `accessLevel: L1` | 双写冲突 | 只保留一个 `owner` 不变量 + 权限集合 |
| `RolePack` 硬编码 UUID | 不可维护 | 落 `role_skill_grants(role_id, skill_id, effect)` |
| `grants.reader/writerRoleIds` | 只有角色维度、无动作维度 | 增加 `grant_permissions(grant_id, subject, action)` |
| `McpTokenScope` | 是令牌维度，不是用户权限 | 保持独立，签发时从用户权限派生并取交集 |

### 7.4 目标数据模型（建议）

```text
permissions            (key, module, name_zh, description, risk_level, default_enabled)
roles                  (id, name, kind: system|custom)
role_permissions       (role_id, permission_key, allowed)
user_permissions       (user_id, permission_key, allowed, granted_by, expires_at)  -- 覆盖角色
user_scopes            (user_id, scope_type: department|role|self|all, scope_id)
approval_policies      (permission_key, require_approval, approver_ids)
mcp_tokens             (principal_id, scope_json, channels, enabled, expires_at)
data_grants            (resource_type, resource_id, subject_type, subject_id, actions[])
```

### 7.5 落地顺序建议

1. 先把 `permissions` 目录和 `role_permissions` 建起来，用现有 L1/L2/L3 生成三套默认模板。
2. 再把 `RolePack`、`grants`、`McpTokenScope` 迁移为数据行，删除硬编码 UUID/中文名正则。
3. 为每个 API 增加统一 `authorize(actor, permission, scope)` 守卫；没有守卫的接口不允许上线。
4. 前端只消费「服务端返回的 allowed 列表」，不做权限推导；按钮权限用同一份 `can()` 结果。
5. 保护区（`PROTECTED_PATH_PATTERNS`）保持硬编码，永不进入勾选。

### 7.6 审核时需要拍板的 5 个问题

1. `L1/L2/L3` 是否保留为「角色模板」，还是完全改成权限点组合？
2. 业务角色 `boss/finance/teaching` 是否并入统一角色体系，还是保留为模块角色？
3. 岗位树（root/child/seat）与「部门」是否合并为一套组织模型？
4. 数据范围（部门/子树/本人）是否独立于权限点配置？
5. MCP 令牌 scope 是否继续独立，还是从用户权限自动派生？

## 九、一句话结论

原项目是「**岗位树 + 角色包 + L1/L2/L3 等级 + MCP 六维 scope + 三态 entitlement + grants**」的叠加模型，**没有可勾选的权限点目录**。若要改成「角色 + 权限点多选」，第一步应先建 `permissions` 目录与 `role_permissions / user_permissions`，并把现有的 `manageMembers / codeScope / grants / RolePack` 拆成动作级 Key；否则只是把现在的多层判断换个前端皮肤，后端仍会出现两套判定标准。
